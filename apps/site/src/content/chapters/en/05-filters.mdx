## The world's most patient librarian

Picture a library with no shelves you can walk along. There's just a counter and a librarian:
the <Term id="relay" locale="en">relay</Term>. You can't wander around. Instead you fill in a
**request slip** and hand it over: "notes by Alice, please" or "anything tagged #nostr since
yesterday". The librarian goes into the back, grabs every matching item, and brings it to the
counter, newest first.

That slip is a <Term id="filter" locale="en">filter</Term>. It's the only way a
<Term id="client" locale="en">client</Term> ever asks a relay for anything. Your timeline, your
notifications, a profile page, a reply thread: under the hood, every screen of every Nostr app is
just a handful of filters.

A filter is a tiny JSON object. Each key is one question about an <Term id="event" locale="en">event</Term>:

- **`authors`**: who signed it? (a list of <Term id="pubkey" locale="en">public keys</Term>)
- **`kinds`**: what sort of thing is it? (`1` = note, `7` = reaction, `0` = profile…)
- **`ids`**: is it one of these exact events? (by <Term id="event-id" locale="en">event id</Term>)
- **`#e`, `#p`, `#t`**: does it carry a <Term id="tag" locale="en">tag</Term> pointing at this event, mentioning this person, or using this hashtag?
- **`since`, `until`**: was it created inside this time window?
- **`limit`**: how many of the newest ones do I want right now?

<Drawer client:visible testid="ch05-uth-wire" locale="en" title="Under the hood: the REQ on the wire">
The JSON in the builder goes over the <Term id="websocket" locale="en">WebSocket</Term> wrapped in a
<Term id="req" locale="en">REQ</Term> message, together with a subscription id you pick:

```json
["REQ", "alice-notes", { "authors": ["e550c6e92808f358382b7b8c14345344f5ef9a299529834d1c26d57b6ace44cc"], "kinds": [1], "limit": 20 }]
```

The relay answers with one `["EVENT", "alice-notes", {…}]` per stored match, then
`["EOSE", "alice-notes"]` (<Term id="eose" locale="en">end of stored events</Term>). The <Term id="subscription" locale="en">subscription</Term> stays open: new matching events
keep arriving until you send `["CLOSE", "alice-notes"]`. With nostr-tools:

```ts
import { SimplePool } from "nostr-tools/pool";
import { matchFilter } from "nostr-tools/filter";

const pool = new SimplePool();
const sub = pool.subscribeMany(
  ["wss://relay.damus.io", "wss://nos.lol"],
  { authors: [alicePubkey], kinds: [1], limit: 20 },
  {
    onevent: (event) => console.log(event.content),
    oneose: () => console.log("stored events done, now streaming live"),
  },
);
// later: sub.close();

matchFilter({ kinds: [1], "#t": ["nostr"] }, someEvent); // the same check, locally
```

Spec: [NIP-01, "Communication between clients and relays"](https://github.com/nostr-protocol/nips/blob/master/01.md#from-client-to-relay-sending-events-and-creating-subscriptions).
</Drawer>

## AND inside the slip, OR between slips

The rules for combining conditions are short enough to fit on a sticky note:

1. **Inside one field, it's OR.** `"authors": [alice, bob]` means *by Alice or by Bob*.
   `"kinds": [1, 7]` means *a note or a reaction*.
2. **Across fields, it's AND.** `{"authors": [alice], "kinds": [1]}` means *by Alice and a note*.
   Every condition you add can only make the result smaller. One failing condition is enough to
   leave an event out (that's what the ✓ and ✗ chips in the "why?" panel show).
3. **Several filters in one REQ are OR-ed.** Want Alice's notes *plus* everyone's reactions to them?
   Send two slips in the same envelope: `["REQ", "sub", {filter A}, {filter B}]`.

<Callout client:visible locale="en" tone="tip" title="Missing field = don't care">
Leaving a field out means "any value is fine". That's why `{}` returns the whole shelf, and why
you never send an empty list like `"kinds": []`: a list with nothing in it can never match.
</Callout>

## Tags: following the threads

Events point at each other through tags, and filters can follow those pointers backwards. The
<Term id="nip01" locale="en">NIP-01</Term> trick is the `#` prefix: `"#x": [...]` matches events that
have a tag named `x` whose **first value** is in the list.

- **`#e`**: everything that points at an event. Replies, <Term id="reaction" locale="en">reactions</Term>,
  reposts and zaps all carry an `e` tag, so `{"#e": [threadId]}` gathers a whole conversation.
- **`#p`**: everything that mentions a person. That's your notifications tab in one line.
- **`#t`**: hashtags. Clients put `#nostr` in the text *and* a `["t", "nostr"]` tag, because relays
  only index tags, never the content.

Try the "Alice's thread" recipe in the builder, then add kind `7`: you've just built a like counter.

## Time windows and limits

`since` and `until` are Unix timestamps (seconds since 1 January 1970), just like an event's `created_at`. An event matches
when `since <= created_at <= until`, both ends included. Apps use them for "load older posts" buttons
(`until` = the oldest thing on screen) and for catching up (`since` = when you last looked).

`limit` is different: it isn't a condition, it's a request about **how many**. The relay sorts
matches newest first and sends at most that many in the first batch. In the builder, matches that
didn't make the cut get a dashed border and a ✂.

<Drawer client:visible testid="ch05-uth-rules" locale="en" title="Under the hood: NIP-01 filter rules">
The fine print, straight from [NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md#from-client-to-relay-sending-events-and-creating-subscriptions):

- `ids`, `authors`, `#e` and `#p` must contain **exact 64-character lowercase hex** values. (Old
  relays accepted prefixes; that was removed, so don't rely on it.) The builder converts `npub1…`,
  `note1…`, `nprofile1…` and `nevent1…` to hex for you, because NIP-19 strings never go on the wire.
- Only **single-letter** tags (`a`–`z`, `A`–`Z`) are indexed, and only by their first value.
  `#d` finds addressable events by identifier, `#a` follows addresses, `#k` finds reactions by the
  kind of thing they react to.
- `limit` only applies to the initial query and is ignored for events that arrive after `EOSE`.
  Relays SHOULD return the newest `limit` events, with ties on `created_at` broken by lowest id,
  and may return fewer. Every relay applies it independently, so asking three relays for
  `"limit": 10` can bring back up to 30 events (minus duplicates, which your client merges by id).
- Relays may cap what they return, refuse expensive filters, or answer with
  `["CLOSED", subId, "reason"]`.

Related extensions: [NIP-45](https://github.com/nostr-protocol/nips/blob/master/45.md) adds
`["COUNT", subId, filter]` to ask *how many* without downloading anything, and
[NIP-50](https://github.com/nostr-protocol/nips/blob/master/50.md) adds a `search` field for
full-text search on relays that support it.
</Drawer>
