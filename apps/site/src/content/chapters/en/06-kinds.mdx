## One envelope, many stamps

So far every <Term id="event" locale="en">event</Term> has looked the same: an id, a <Term id="pubkey" locale="en">pubkey</Term>,
a timestamp, some tags, some content and a signature. A tweet-style note, your profile, a "like",
a blog post and a Lightning receipt all travel in **the exact same envelope**.

So how does an app know which is which? One tiny field: the <Term id="kind" locale="en">kind</Term>.
It's just an integer, like a stamp on the envelope. `1` means "short text note", `0` means "my profile",
`7` means "reaction", `30023` means "long-form article". That's it. No new message types, no new
endpoints: Nostr grows by inventing new numbers.

Think of the kind as the **section of a library**. The books (events) are all bound the same way, but
the sticker on the spine tells the librarian (the <Term id="relay" locale="en">relay</Term>) which shelf
to put it on, and tells readers (clients) how to display it.

## Four ways to be stored

The number tells a relay what to *keep*. <Term id="nip01" locale="en">NIP-01</Term> splits the
number line into four neighborhoods:

- **Regular** (`1`, `2`, `4`–`44`, `1000`–`9999`): a diary. Every page is kept. Notes, reactions,
  reposts and zap receipts pile up forever (or until the relay decides otherwise).
- **<Term id="replaceable-event" locale="en">Replaceable</Term>** (`0`, `3`, `10000`–`19999`): a whiteboard.
  Each person gets **one** per kind; writing a new one wipes the old. Your profile (<Term id="metadata" locale="en">kind 0</Term>),
  your <Term id="follow-list" locale="en">follow list</Term> (kind 3) and your relay list (kind 10002) work this way.
- **<Term id="ephemeral-event" locale="en">Ephemeral</Term>** (`20000`–`29999`): a phone call. Relays pass it to
  whoever is listening *right now* and then forget it. Perfect for login challenges and signer chatter.
- **<Term id="addressable-event" locale="en">Addressable</Term>** (`30000`–`39999`): a set of labeled
  whiteboards. One per person, per kind, **per `d` tag**. That's how you can edit several
  <Term id="long-form" locale="en">long-form articles</Term> independently.

<Callout client:visible locale="en" tone="tip" title="Who wins a tie?">
For replaceable and addressable events the newest `created_at` wins. If two versions share the exact
same second, relays keep the one with the **lowest id** (first in alphabetical order), so every relay
ends up agreeing on the same winner no matter which copy arrived first.
</Callout>

<Drawer client:visible testid="ch06-uth-storage" locale="en" title="Under the hood: NIP-01 storage rules">
The exact rules from [NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md#kinds):

| Category | Range | Relay keeps |
|---|---|---|
| regular | `1000 <= n < 10000 \|\| 4 <= n < 45 \|\| n == 1 \|\| n == 2` | every event |
| replaceable | `10000 <= n < 20000 \|\| n == 0 \|\| n == 3` | latest per `(pubkey, kind)` |
| ephemeral | `20000 <= n < 30000` | nothing (forward only) |
| addressable | `30000 <= n < 40000` | latest per `(pubkey, kind, d)` |

Kinds 45–999 and 40000–65535 fall outside every range: NIP-01 says nothing about storing them, and most
relays treat them as regular. An addressable event is pointed at with its *address* `kind:pubkey:d`, either
in an `a` tag or encoded as an <Term id="naddr" locale="en">naddr</Term>:

```json
["a", "30023:e550c6e92808f358382b7b8c14345344f5ef9a299529834d1c26d57b6ace44cc:relays-explained", "wss://relay.alpha.example"]
```

Asking for "the current version" is a normal filter, because the relay only stores one:

```json
["REQ", "article", { "kinds": [30023], "authors": ["e550c6…"], "#d": ["relays-explained"] }]
```
</Drawer>

## NIPs: how Nostr grows without a boss

Who decides that `7` means "reaction"? Nobody, and everybody. A <Term id="nip" locale="en">NIP</Term>
(*Nostr Implementation Possibility*) is a short, public document describing a convention: which kind
to use, which tags, what the content means. They live in one GitHub repository, but they work more like
recipes shared at a potluck than laws:

1. **Someone has an idea.** A developer wants polls, or calendars, or marketplaces.
2. **They build it first.** Ideally in a real client and relay, picking a kind number nobody else uses.
3. **They open a pull request.** People argue, simplify, and poke holes in it in public.
4. **It gets merged when it's real.** The README asks that a NIP be implemented in at least two clients
   and one relay (where applicable), make sense, be optional and backwards-compatible, and not add a second way
   to do the same thing.

The key trick is the word *optional*. A client that doesn't understand kind `31922` (a calendar event)
simply ignores it. Nothing breaks. That's why Nostr can grow sideways: microblogging, long-form,
livestreams, code collaboration and wallets all share the same relays and the same keys.

<Callout client:visible locale="en" tone="info" title="NIP names are not always numbers">
Most NIPs have two-digit decimal names (`01`, `57`), but newer ones may use hex-looking names such as
`7D` (threads) or `C7` (chats). The kind number and the NIP number are unrelated: kind `7` is defined
in NIP-25, not NIP-07.
</Callout>

<Drawer client:visible testid="ch06-uth-nips" locale="en" title="Under the hood: NIPs worth reading">
Useful starting points in the [NIPs repository](https://github.com/nostr-protocol/nips):

- [NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md): the event format, kind 0 and the four storage categories (kind 1 is specified in [NIP-10](https://github.com/nostr-protocol/nips/blob/master/10.md))
- [NIP-02](https://github.com/nostr-protocol/nips/blob/master/02.md): follow list (kind 3)
- <Term id="nip23" locale="en">NIP-23</Term> ([spec](https://github.com/nostr-protocol/nips/blob/master/23.md)): long-form content (kind 30023, drafts 30024)
- [NIP-51](https://github.com/nostr-protocol/nips/blob/master/51.md): lists, standard (10000+) and sets (30000+)
- [NIP-65](https://github.com/nostr-protocol/nips/blob/master/65.md): relay list metadata (kind 10002)
- [NIP-31](https://github.com/nostr-protocol/nips/blob/master/31.md): put a human-readable `alt` tag on custom kinds, so clients that don't understand them can still show *something*. The NIPs README now marks NIP-31 as unrecommended, but an `alt` tag on a custom kind is still a harmless courtesy
- [NIP-89](https://github.com/nostr-protocol/nips/blob/master/89.md): apps announce which kinds they handle (31990), users recommend apps (31989)

Inventing a private kind for your app? Pick an unused number in the right range for the storage
behavior you want, add an `alt` tag, and document it.
</Drawer>
